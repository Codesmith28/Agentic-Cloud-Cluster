# BTEP Reliability, Observability, PPO Evidence, and Test Campaign Plan

## Summary

- Deliver this in six branches, merged in order, with documentation updated in each branch.
- Hard-remove GPU from the project surface so the system, benchmarks, and claims are CPU/memory/storage only.
- Build at-least-once failure recovery around execution attempts so dead-worker tasks are requeued automatically and late results cannot corrupt final task state.
- Add Prometheus and Grafana to the DinD testbench, with exported benchmark artifacts for every run.
- Keep the current PPO serving/inference path for real-world adaptation. Add public-trace and replay-based training/evaluation as an additional offline data pipeline, not a replacement.
- PPO data strategy:
  - primary public pretraining/evaluation corpus: [Alibaba Cluster Trace Program `cluster-trace-v2018`](https://github.com/alibaba/clusterdata)
  - secondary external holdout: [Google ClusterData2019](https://github.com/google/cluster-data)
  - internal domain adaptation corpus: CloudAI Mongo history
  - online adaptation: live CloudAI cluster outcomes after deployment
- Observability implementation follows [Prometheus Go instrumentation](https://prometheus.io/docs/guides/go-application/) and [Grafana provisioning](https://grafana.com/docs/grafana/latest/administration/provisioning/). Public-trace selection is guided by the user-supplied [MDPI paper](https://www.mdpi.com/2073-431X/14/12/560).

## Branches

1. `codex/gpu-hard-removal`
   - Remove GPU fields from gRPC proto, DB models, scheduler/task typing, worker telemetry, benchmark metrics, testbench env vars, and docs.
   - Supported task types become `cpu-light`, `cpu-heavy`, `memory-heavy`, `mixed`.

2. `codex/recovery-attempt-requeue`
   - Introduce logical task vs execution attempt semantics.
   - Add `attempt_id` and `attempt_no` to assignment, heartbeat running-task reporting, and completion reporting.
   - Persist per-attempt lifecycle in a new attempts store; keep `TASKS` as logical task state and `RESULTS` as canonical final result.
   - On heartbeat timeout, worker death, or master restart, mark active attempts on that worker as `lost`, release reserved resources, and enqueue a new attempt unless the task is already terminal.
   - Accept only the currently active attempt as canonical completion; stale attempt results are stored for audit but cannot overwrite the task outcome.
   - Expand startup recovery to restore `queued`, `pending`, and stranded active attempts.
   - Add read-only task-attempt inspection to the HTTP API and recovery fields in task detail responses.

3. `codex/prometheus-grafana-observability`
   - Add `/metrics` on master and worker using Prometheus client libraries.
   - Keep labels low-cardinality: `scheduler`, `task_type`, `status`, `worker_id`, `failure_reason`; never `task_id` or `attempt_id`.
   - Master metrics: queue depth, enqueue/dequeue rates, scheduling latency histograms, scheduler selections, task terminal counters, worker timeout/requeue/stale-result counters, recovery duration histograms.
   - Worker metrics: heartbeat freshness, running task gauge, image pull/start/runtime histograms, Docker error counters, resource gauges, aggregated container CPU/memory/IO stats by task type.
   - Extend the DinD testbench with Prometheus, Grafana, provisioned data source/dashboards, and a run collector that exports Prometheus range queries plus master summaries to per-run JSON/CSV artifacts.
   - Dashboards: cluster overview, scheduler/queue, recovery incidents, worker/runtime, benchmark summary.

4. `codex/deterministic-workflow-images`
   - Replace ad hoc `alpine` shell tasks in the evidence suite with a versioned deterministic workflow image set.
   - Use one pinned base benchmark image with subcommands for `cpu-light`, `cpu-heavy`, `memory-heavy`, `mixed`, plus helpers for `exit-nonzero`, `hang`, and `slow-start`.
   - Update workload manifests used for benchmarking to reference fixed image tags and parameter blocks instead of free-form benchmark commands.
   - Keep DinD workers as the execution substrate so tasks still run inside worker-scoped Docker daemons with CPU/memory/storage caps.

5. `codex/trace-replay-ppo`
   - Keep the current PPO runtime integration and online adaptation path intact.
   - Add a parallel offline data/training/evaluation pipeline driven by replayable traces.
   - Normalized trace schema: arrival time, requested CPU/memory/storage, task type, worker snapshot/capacities, actual runtime, queue wait, SLA outcome, failure/requeue annotations.
   - First-class trace sources:
     - internal CloudAI Mongo history
     - [Alibaba `cluster-trace-v2018`](https://github.com/alibaba/clusterdata) as primary public pretraining/eval corpus
     - [Google `ClusterData2019`](https://github.com/google/cluster-data) as external holdout
   - v1 adapter behavior: flatten public trace jobs to per-task arrivals; ignore DAG edges because the current system is task-based, not workflow-DAG aware.
   - PPO lifecycle:
     - synthetic env retained for smoke tests and interface regression checks
     - offline pretraining on Alibaba traces
     - offline domain adaptation on CloudAI history
     - evaluation on held-out Alibaba windows, Google holdout, and CloudAI replay
     - online fine-tuning on live CloudAI outcomes, gated behind config
   - Extend the benchmark/report path so simulation compares `Round-Robin`, `RTS`, and `PPO`, and live runs can evaluate PPO models from different training stages.

6. `codex/evidence-benchmark-campaign`
   - Build the final automated campaign runner around DinD workers, Prometheus collection, failure injection, and report generation.
   - Normal suites: `RR`, `RTS`, `PPO-pretrained`, `PPO-adapted`.
   - Failure suites: `RR+recovery`, `RTS+recovery`, `PPO+recovery`.
   - Produce a reproducible evidence bundle per campaign: workload manifest, cluster profile, Prometheus export, task-attempt timeline, scheduler summary tables, and markdown/html report.
   - Update root and testbench documentation for every new mechanism, including access URLs for Prometheus/Grafana and exact benchmark commands.

## Implementation Changes

- Recovery model
  - `AssignTask`, heartbeats, running-task reporting, and completion reporting carry `attempt_id`.
  - Resource reservations attach to attempts, not just task IDs.
  - One recovery manager owns timeout detection, orphan detection, resource release, and requeue decisions.
  - Failure reasons are explicit: `worker_timeout`, `worker_killed`, `docker_daemon_down`, `master_restart`, `image_pull_failed`, `container_failed`, `late_result`.

- PPO data/training model
  - Existing PPO inference service remains the production scheduler endpoint.
  - Add model lineage metadata: `model_source`, `training_corpus`, `trace_window`, `cluster_fingerprint`, `train_timestamp`.
  - Add offline replay tooling without changing live RPC behavior.
  - Add deployment modes:
    - `shadow`: PPO scores decisions but does not control placement
    - `active`: PPO controls placement
    - `fallback`: RTS or RR on PPO unavailability or policy rejection
  - Online adaptation uses only CloudAI outcomes and preserves rollback to the last validated model.

- GPU removal
  - Remove GPU fields from proto, Go models, worker env vars, scheduler math, executor code, benchmark metrics, docs, and workload files.
  - Delete GPU task-type inference and GPU benchmark profiles; replace any prior GPU examples with CPU/memory/mixed equivalents.

- Benchmark/testbench
  - Cluster profiles:
    - `hetero-small`: current 3-node small/medium/large profile
    - `hetero-imbalanced`: one strong node plus four weak nodes
    - `recovery-lab`: three nodes with scripted kill/restart and daemon-failure actions
  - Workload suites:
    - `steady-cpu`
    - `steady-mixed`
    - `memory-pressure`
    - `bursty`
    - `long-tail`
    - `failure-stressed`
  - Failure injectors:
    - kill worker container
    - pause/disconnect worker to simulate heartbeat loss
    - kill DinD daemon
    - bad image tag for pull failure
    - container command failure
    - master restart with queued and running work present
    - stale-result replay after requeue

## Evidence and Targets

- Default acceptance targets
  - PPO median makespan improvement vs `Round-Robin`: `15-25%` on heterogeneous and bursty suites.
  - SLA violations: `<5%` on dynamic and failure suites.
  - Throughput gain vs `Round-Robin`: `>=10%` under saturated heterogeneous load.
  - P95 queue wait: `>=20%` lower than `Round-Robin` and no more than `25%` of the task SLA deadline on accepted runs.

- Measurement set
  - Scheduler: decision latency, queue depth, queue wait, makespan, throughput, balance score, unschedulable count.
  - Reliability: requeue count, recovery latency, stale-result count, lost-attempt count, duplicate-suppression count, completion rate under failure.
  - Runtime: image pull/start/runtime, worker CPU/memory/storage utilization, container CPU/memory/IO.
  - Control plane: heartbeat gaps, master API latency, DB latency/error rate.
  - PPO-specific: reward trend, action entropy, policy confidence, fallback rate, shadow-vs-active divergence, model version performance deltas.

- Repetition protocol
  - Simulation/replay: 20 seeds or shuffled replay windows per profile per scheduler.
  - Live DinD runs: 5 repetitions per profile per scheduler with fixed workload manifests.
  - Report median, p95, and 95% confidence intervals.

- Evidence package
  - Fast evidence: replay benchmark artifacts for `RR/RTS/PPO`.
  - Strong evidence: live DinD campaigns with Prometheus-backed time series and failure injection.
  - Generalization evidence:
    - pretrained on Alibaba, tested on Google and CloudAI replay
    - adapted on CloudAI history, tested on live cluster
    - shadow-mode evidence before active PPO rollout

## Assumptions

- CRIU/live migration is out of scope for this phase; failure-aware requeue/reschedule is the reliability mechanism we will claim.
- Recovery claim is `at-least-once execution with duplicate suppression`, not exactly-once.
- Network emulation is out of scope for v1; heterogeneity is defined by CPU/memory/storage caps and failure injection.
- Public traces are used for offline pretraining and evaluation, not as a replacement for real-world CloudAI adaptation.
- Synthetic PPO environments are retained only for smoke/regression validation, not for final evidence claims.
